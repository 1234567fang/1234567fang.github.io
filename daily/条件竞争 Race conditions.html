Deyu's Blog

大多数网站通过多个线程处理并发请求，所有读写都来自一个共享的数据库。应用代码很少考虑并发的风险，因此网络上经常出现条件竞争。也就是说网站服务器来不及处理多余的请求，导致多个不同的线程同时与相同的数据交互，从而导致“冲突”，从而导致应用程序中出现意外行为。
注意条件竞争不仅限于特定网页应用架构，常见的还有数据库，部分中间件等。
漏洞利用通常是使用限额超载——它们通过同步请求来突破某种限制，比如：
多次兑换礼品卡
重复利用优惠券
多次给产品刷评分
提现或者转账超过账户余额的现金
重复使用同一个验证码
绕过反暴力破解速率限制
以上都利用了安全检查与受保护动作之间的时间间隙（碰撞窗口）
repeater测试

突破限额

最常见的条件竞争
状态检查存在时间差
靶场：Limit overrun race conditions
购买夹克衫但钱不够，尝试利用优惠价
猜测流程是结账时从数据库中查看当前session的折扣是否使用，如果没有使用则应用到购物车的总金额中，并将数据库的折扣设置为已使用。
利用的是 “检查优惠券状态并使用” 与 “标记优惠券为已使用” 这两个数据库操作之间的竞争窗口

靶场：Lab: Bypassing rate limits via race conditions | Web Security Academy
对登录作了次数限制来防止爆破，尝试绕过
逻辑是一个用户名尝试3次后就会锁定，因此尝试次数与用户名相关联而不是session，考虑的情况是提交登录尝试和网站增加与特定用户名关联的失败登录尝试次数的计数器之间存在竞争窗口

简单说，就是利用“登陆时检查当前次数”与“登陆过次数+1”这之间的竞争窗口
实现：攻击者同时（使用单数据包攻击）发送 N个 使用同一个错误密码的登录请求，这n个请求需要同时到达服务器。同时服务器会并行处理这些请求（涉及架构设计与运行多线程，可以理解为银行）
需要py或者turbo Intruder
BurpSuite已经有了intruder模块为什么还要用这个插件，问题的原因就是并发是指的是抢在同一时间发送所有数据包，而intruder模块是无法做到的。

隐藏的步骤

一个单个请求实际上背后可能隐藏有多个子状态的转换
靶场：2FA simple bypass
猜测实际逻辑可能是：

  1. 判断用户名密码是否正确，正确则生成可以使用的session
  2. 接着跳转到 /login 页面，要求输入2FA code
  3. 如果输入正确则跳转到最后的account账户页面，如果输入错误则将session设置为无效。

2FA Code 是 双因素认证验证码，全称是 Two-Factor Authentication Code。它是一种在用户输入用户名和密码后，必须提供的第二道动态安全凭证。比如邮箱，Steam，QQ微信，Wegame。

这套逻辑的关键就在于拿生成的session直接访问账户页面，绕过了2FA Code
为什么？应用在验证了用户名和密码正确后，立即将用户标识（如userid）写入会话（Session），然后才跳转到要求输入2FA Code的页面。攻击者可以在跳转之前，直接使用这个已认证的会话访问需要登录后才能进入的主页。

实现：在通过验证后，响应包中会返回一个已设置 session['userid'] 的Cookie，此时忽略服务器的2FA要求，带着这个包含session的cookie访问 my-account等受保护页面，核心是找未授权接口。

多端点竞争

多端点的条件竞争-single connection
靶场：Lab: Multi-endpoint race conditions | Web Security Academy
逻辑正常是

  1. 将商品添加到购物车
  2. 付款：POST /cart/checkout
  3. 确认订单：GET /cart/order-confirmation?order-confirmed=true

存在的漏洞就是在确认订单的时候，没有充足的验证，没有验证当前购物车的总金额和最后付款的金额是否一致，导致了攻击。
攻击者的流程是：

  1. 先将便宜的商品添加到购物车中（必要）
  2. 付款：/cart/checkout
  3. 将jacket添加到购物车中
  4. 确认订单：GET /cart/order-confirmation?order-confirmed=true

想要实现条件竞争有两个端点，一个是POST /cart将商品添加到购物车中，一个是GET /cart/checkout付款并确认订单。

在进行多端点条件竞争时最容易会遇到的是，使用单数据包并发的时候，需要/难以对齐每个请求的竞争窗口。
为什么难以对齐：因为在多端点或复杂单端点攻击中会包含两种情况
一：网络架构引入的延迟：例如，前端服务器每次与后端建立新连接时可能会有延迟。使用的协议也可能有重大影响。（这种由后端延迟造成的一般不会影响并发，可以忽略。因为它会同等地延迟并行请求，导致这些请求虽然存在延迟，但是彼此仍然算是同步的）使用连接预热来解决。
二：端点特定处理引入的延迟：不同的端点在其处理时间上天生就存在差异，有时这种差异取决于它们触发了什么操作。（如果连接预热没有造成差别，那说明可能确实是由端点特定因素引起，这种有两种处理方法…）
第一种就是引入短暂的客户端延迟，即通过多次请求确定两个端点之间延迟差别的时间，让处理更快的请求之前加上这么一个短暂的延迟。相应的就会导致无法使用单数据包攻击技术。
第二种方法是利用一项常见的安全功能。如果发送请求过快且数量过多，Web服务器通常会延迟处理这些请求。通过发送大量虚假请求故意触发速率或资源限制，可以造成适当的服务器端延迟。这种情况使得单数据包攻击变得可行。

为什么需要对齐：如果不将它们“对齐”到同一时间点到达易受攻击的代码段，攻击就会失败。例如取钱，查询余额有没有足够的钱和取出对应的钱，当攻击者使用并发，确保两个请求完全交错。数据库执行取钱的操作意外的快于查询余额的操作，会导致余额回滚。如果对齐失败，攻击者使用并发但其中“取款请求”因更复杂而更慢的执行，取款已经覆盖了查询，余额已经变成了零。

当写入操作完全并行时，数据库可能以任意顺序处理它们

单端点竞争

向单一端点发送不同值的并行请求有时会触发严重的条件竞争
现实中生成邮箱确认和基于邮箱的操作通常都有存在单端点条件竞争的可能：因为电子邮件通常在服务器向客户端发出HTTP响应后，在后台线程中发送，修改账户邮箱时，发送验证邮件和更新数据库的操作之间存在竞争窗口，可能导致邮件内容错乱，劫持账户等。
靶场：Lab: Single-endpoint race conditions | Web Security Academy
逻辑产生漏洞的原因是在更改电子邮件时，会更新user.unconfirmed_email，将token保存在user.confirmation_token中（这一步理解为在更新数据库）但在构造邮件内容的时候，email和token都是从数据库中提取的（发送邮件依赖数据库）可知写入数据库和发邮件之间存在碰撞窗口

正常流程是先更新数据库（更新邮箱）->发送邮件，但攻击者发现存在这么一个竞争窗口，第一次更新邮箱请求发送后，后端会发送电子邮件。在邮件发送前，后端处理了第二个更新邮箱请求，将第二个邮箱地址和token写到了数据库中。因此如果第一次发送的邮件内容出现了第二次的邮箱，就说明竞争成功。
将流程变成了更新数据库（更新邮箱）->再次更新数据库进行覆盖->发送邮件
此时发送的邮件，通过数据库查到的邮箱已经是进行覆盖过的邮箱地址，也就造成了第二者接管。

部分构造竞争

时间敏感攻击

防护

  • 避免混合使用不同来源的数据。
  • 确保敏感的端点利用数据存储的并发特性来保证状态的改变是原子化的。例如，使用单独的数据库事务来检查支付金额是否与购物车价值匹配并确认订单。
  • 利用数据存储的完整性和一致性特征(如唯一性约束)来作为深度防御措施，
  • 不要试图使用一个数据存储层来保护另一个。例如，不要用session来保护数据库不受limit-overrun攻击
  • 确保您的session处理框架保持session的内部一致性。
  • 某些架构可能非常适合不在服务器端保存状态信息，可以使用加密技术(例如JWT)将状态信息存储在客户端。但使用JWT也并不是完全没有风险。
