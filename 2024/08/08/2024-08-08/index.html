CSRF

[!NOTE]
客户端请求伪造（低危）
指利用受害者尚未失效的身份认证信息（cookie、会话等），诱骗其点击恶意链接或者访问包含攻击代码的页面，在受害人不知情的情况下以受害者的身份向（身份认证信息所对应的）服务器发送请求，从而完成非法操作

c用户–登录—>A站(csrf漏洞)
C用户点击了b用户发的恶意链接
b以c用户的身份向a站发送了功能请求
CSRF与XSS最大的区别就在于，CSRF并没有盗取cookie而是直接利用

CSRF最关键的是利用受害者的cookie向服务器发送伪造请求
XSS->客户端 不需要登录
CSRF->服务端 有伪装的登录信息
每个浏览器的Cookie是独立存储的，互相独立不共享，生成登录链接也不会生效

通过使用短链接来隐藏URL，进行欺骗
具体步骤：
1、进入需要的操作界面f12扒取原代码（复制元素）或者BP劫持操作请求
2、生成poc作为文件，修改后缀为html（BP相关工具一键）
3、给用户点击（会以POST形式进行表单传输）

危害：
1、对网站管理员进行攻击
2、修改受害网站上的用户账户和数据
3、账户劫持（改邮箱等）
4、传播CSRF蠕虫进行大规模攻击
5、利用CSRF进行拖库
6、利用其他漏洞进行组合拳攻击
7、针对路由器的CSRF攻击

防御方法：
同源策略及跨域

  • 阻止不明外域的访问:
  • 同源检测-检测referer来源。但是一般可伪造（目录，路径）
  • Samesite Cookie-设置Samesite=Strict严格模式，相当于没有cookie，坏处就是再次进入都要重新登录(同站不需要)，而且不支持子域名。
  • 提交时要求附加本域才能获取的信息:
  • CSRF Token-设置随机Token。如果设置这个参数就不存在漏洞，一般在数据包中就可以直接判断出。但可能存在伪随机、未设置时间戳，几个Token来回使用。
  • 双重Cookie验证-后端接口验证Cookie中的字段与URL参数中的字段是否一致，不一致则拒绝，但存在XSS时攻击者可以注入Cookie，那么该防御方式失效。

每个Cookie的属性，包括：
Name：Cookie的名称
Value：Cookie的值
Domain：Cookie适用的域
Path：Cookie适用的路径
Expires/Max-Age：Cookie的过期时间
HttpOnly：如果设置则该Cookie无法通过JavaScript访问,可能能够通过XSS攻击窃取Cookie
Secure：如果设置则该Cookie仅在HTTPS连接中发送,可能能够通过中间人攻击窃取Cookie

Cookie和Session的区别：
Cookie：身份认证，存储在本地，cookie用来携带JSESSIONID 不能超过4KB
Session：会话控制，存储在服务器，会产生大量session对性能有影响 使用session需要cookie的配合，安全与保密性好
cookie和session必须在同一浏览器
session和cookie本质上是一样的，都是通过HTTP请求包中的cookie进行传输，只是服务端的处理过程不一样，对于Cookie来说，用户数据直接就在请求头当中，服务端直接获取使用，而对于session来说，请求头中的cookie只是一个名称，真正的数据存储在服务端中，服务端通过这个名称去读取文件或数据库获取真正的内容

点击劫持

点击劫持是一种视觉上的欺骗手段。
攻击者使用一个透明的、不可见的 iframe，覆盖在一个网页上，然后诱使用户在该网页上进行操作，此时用户将在不知情的情况下点击透明的 iframe 页面。通过调整 iframe 页面的位置，可以诱使用户恰好点击在 iframe 页面的一些功能性按钮上，比如提交表单。点击劫持需要对页面布局，调整按钮的位置，引导用户点击。隐藏 iframe 很容易，设置 opacity 为 0，或者让 iframe 设置成绝对定位，把 z-index 设置很多，让它处在最上层。

预防方法：

  • 使用 JavaScript 来禁止内嵌
  • X-Frame-Options
    这是一个 HTTP 响应头，专门用于防止点击劫持攻击。他有三个可选值：
    1、DENY
    表示该页面不允许在frame中展示，即便是在相同域名的页面中嵌套也不允许。
    2、SAMEORIGIN
    表示该页面可以在相同域名页面的frame中展示。通常使用此项。
    3、ALLOW-FROM uri
    表示该页面可以在指定来源的frame中展示。

OAuth劫持

认证缺陷
一些网站经常让我们绑定微信、绑定qq，在绑定微信或者qq的时候，抓包找到我们绑定的包
把那个包要丢弃但是链接我们要留下来 只需要把这个链接发给受害者即可 受害者的网站即可绑定我们的这个微信号或者qq号
受害者点击链接，将服务器给与的用于账户绑定的特定cookie让受害者绑定，以后用微信等平台扫码登录，直接就是受害者的账户

CSRF挖洞

  • 典型：删除文章（/delete?article_id=123）、点赞（/like?post_id=456）、修改个人邮箱（/profile?signature=hack）；
  • 示例：目标删除操作 URL：http://target.com/delete?user_id=789攻击者构造恶意链接：http://target.com/delete?user_id=789，诱导用户点击后，其账号下的资源被删除。
  • 测试优先级：账号权限类：修改密码、绑定手机 / 邮箱、修改安全问题、注销账号；
  • 资源控制类：添加 / 删除用户（管理员功能）、修改用户权限、创建角色；
  • 数据操作类：转账、发起交易、删除重要数据（如订单、日志）；
  • 配置修改类：修改系统配置（如开放 API、允许外部访问）、修改防火墙规则。

SSRF

[!NOTE]
服务器请求伪造

攻击者利用SSRF漏洞通过服务器发起伪造请求，这样就可以访问到内网的数据，进行内网信息探测，内网漏洞利用，结合文件包含读取，绕过防火墙以及进行dos攻击。
SSRF漏洞形成的原因是应用程序存在可以从其他服务器获取数据的功能，但是服务器的地址并没有做严格的过滤，导致应用程序可以访问任意的URL链接，攻击者通过精心构造URL链接，可以通过SSRF漏洞进行以下攻击.
有回显-高危 无回显-低危
分享 翻译 外部头像

与远程文件包含漏洞的区别：远端加载进来就是SSRF,不生效就是远程文件包含
与URL重定向：有回显当前页面内套娃就是SSRF，否则重定向
看返回包 302则重定向 200则SSRF

利用方式：以下四种协议

[!NOTE]
绕过手法：
302跳转，sudo cc会重定向到127.0.0.1 xray oob平台可以生成302
添加@ 特殊数字例如②绕过（限制域名时）忽略 @ 前的内容，# 后面的内容忽略
点分割符号替换 例如。
DNS欺骗 如不同的本地环回地址（xip.io)
DNS重绑
IP转换（八，十六等不同进制）
CRLF编码绕过CRLF
防御方法：
禁止302跳转，或者每跳转一次都进行校验目的地址是否为内网地址或合法地址。
过滤返回信息，验证远程服务器对请求的返回结果，是否合法。
禁用高危协议，例如：gopher、dict、ftp、file等，只允许http/https。
设置URL白名单或者限制内网IP。
限制请求的端口为http的常用端口，或者根据业务需要开放远程调用服务的端口。
catch错误信息，做统一错误信息，避免黑客通过错误信息判断端口对应的服务。

ssrf攻击redis数据库

启动服务：redis-server redis-4.0.10/redis.conf
redis直接连接：redis-cli -h xxx.xxx.xxx.xxx
默认无密码，redis.conf配置文件中确认requirepass参数是否设置密码，默认端口6379,自定义端口空格加端口号‌‌
判断未授权的关键：

  • bind x.x.x.x
    配置允许登陆 redis 服务的 ip，默认是 127.0.0.1(本机登录)
    如果设置成 0.0.0.0 就相当于将redis暴露在公网中，公网中的机器都可以进行登陆
  • protected-mode
    功能是自 redis 3.2 之后设置的保护模式，默认为 yes，其作用就是如果 redis 服务没有设置密码并且没有配置 bind 则会只允许 redis 服务本机进行连接

一些公共 http 域名，但是解析到 127.0.0.1
如下绕过waf（localhost）
http://safe.taobao.com/
http://114.taobao.com/
http://wifi.aliyun.com/
http://imis.qq.com/

判断成功：
基于DNS记录判断：dnslog外带是否有记录
基于 HTTP 请求判断：自己搭建服务器，看日志记录
基于时间差判断：请求一个需要耗费较长时间的资源，看正常请求和SSRF请求的时间
基于错误信息判断：错误信息包含服务器内部的路径、IP 地址或内部错误代码，如 Failed to connect to 127.0.0.1 或 Permission denied
